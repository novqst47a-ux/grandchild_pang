## 1. 목적과 성공 기준

`webapp/`의 현재 UI는 **보라(`--purple #65419a`) + 크림** 톤에 모든 요소가 동일한 립 그림자를 갖고 있어,
게임 화면과 설정 화면의 구분이 시각적으로 없다. DESIGN.md는 이를 다음 대비로 재정의한다.

> **게임 영역은 입체(3D 립) · 모달은 평평(플랫)**, 전체 톤은 따뜻한 크림/주황.

리뉴얼 완료의 판단 기준은 아래 네 가지다.

| # | 성공 기준 | 검증 방법 |
|---|---|---|
| S1 | 게임 영역의 모든 조작 요소가 자기 색의 어두운 립을 갖고 누르면 내려간다 | 실기기 육안 + 코드 리뷰 |
| S2 | 모달 안에 립(`box-shadow: 0 Npx 0`)과 bounce 이징이 하나도 없다 | `tests/design-tokens.test.mjs` 자동 검사 |
| S3 | 사용자에게 보이는 모든 문구가 §7 보이스·톤 규칙을 지킨다 (`-습니다`·금지어 0건) | 자동 문구 검사 |
| S4 | 텍스트 조합 대비 4.5:1 이상, 구조 경계 3:1 이상 | `scripts/check-contrast.mjs` 자동 검사 |

기능(게임 규칙, 저장 방식, 사진 파이프라인)은 **변경하지 않는다.** 이번 작업은 표현 계층과 문구, 그리고 그에 필요한 최소한의 렌더 로직만 다룬다.

### 2.2 반드시 짚어야 할 현재 코드의 문제

1. **`sw.js`의 `ASSETS`에 `styles.css`가 없다** (`webapp/sw.js:2`).
   프리캐시 목록에 없어도 fetch 핸들러가 cache-first로 응답을 저장하므로, 캐시 이름을 올리지 않으면
   **기존 사용자에게 구 CSS가 계속 서빙된다.**

   > **Phase 1에서 실제로 발생했다.** 토큰을 전부 교체했는데 브라우저는 구 보라색을 그대로 렌더했다.
   > 캐시를 열어 보니 `sonjupang-mvp-v4`가 `/styles.css`뿐 아니라 **`/@vite/client`와
   > `node_modules/.vite/deps/*`까지** 담고 있었다. 즉 이 서비스 워커는 개발 중 HMR을 통째로 죽인다.
   >
   > 배포 리스크로만 적어 두었지만 모든 Phase의 검증을 막으므로 **Phase 5 → Phase 1로 앞당겨 처리했다.**
   > ① `CACHE`를 `v5`로 올리고 `ASSETS`에 `./styles.css` 추가,
   > ② `import.meta.env.PROD` 가드로 개발 서버에서는 서비스 워커를 등록하지 않는다.
   > 프로덕션 빌드에는 등록 코드가 그대로 남는 것을 `dist` 산출물에서 확인했다.

2. **핀치 줌이 차단되어 있다** (`webapp/index.html:5`의 `maximum-scale=1, user-scalable=no`).
   → **[결정 D5](#d5-핀치-줌-차단-유지)에 따라 차단을 유지한다.** 게임 중 의도치 않은 확대로 인한
   조작 오차가 더 큰 문제라는 판단이다. 대신 "크게 보고 싶다"는 요구는 남으므로
   §6.1 A8(rem 기반 타이포)과 B1(블록 크기 선택)으로 대체한다.
   DESIGN §12 체크리스트의 "확대 200% 상태 확인" 항목은 **수행 불가로 처리하고 제외**한다.

3. **입체감을 `drop-shadow`로 흉내내고 있다** (`webapp/styles.css:98`).
   DESIGN §5.4가 명시적으로 금지한 방식이다.

4. **전체 초기화가 네이티브 `window.confirm()`을 쓴다** (`webapp/src/app.js:558`).
   DESIGN §9는 별도 확인 다이얼로그 + 기본 포커스 **취소**를 요구한다. 네이티브 confirm은
   문구·색·포커스를 제어할 수 없고, WebView에서 시스템 폰트로 튀어나와 톤이 깨진다.

5. **선택지가 가로 스크롤로만 접근된다** (`webapp/styles.css:172`의 `.slot-list, .frame-list`).
   DESIGN §11 Don't에 정면으로 어긋난다.

## 3. 작업 단계

각 단계는 독립 커밋/PR로 나눈다. 단계마다 `npm.cmd test && npm.cmd run check && npm.cmd run build`가 통과해야 다음으로 넘어간다.

### Phase 0 — 안전망 (0.5일)

리뉴얼 자체보다 **먼저** 넣는다. 이후 단계의 회귀를 자동으로 잡기 위한 장치다.

- [ ] `webapp/tests/design-tokens.test.mjs` 신규 — 아래를 자동 검사
  - `--purple` / `--cream` 등 구 토큰 잔존 0건
  - `color: var(--carrot)` 형태의 **밝은 주황 위 텍스트** 사용 0건
  - `font-weight` 값이 `400 / 700 / 800 / 900` 집합 밖이면 실패
  - 모달 선택자(`.settings-dialog` 이하) 안에 `box-shadow: 0 Npx 0` 립 0건
  - `index.html` 텍스트 노드 + `app.js` 문자열 리터럴에 `-습니다` 및 금지어(`오류`, `실패`, `잘못`, `불가능`, `데이터가 없습니다`) 0건
- [ ] `package.json`의 `check` 스크립트에 위 두 개 연결
- [ ] 리뉴얼 전 기준값 확보 (360 / 390 / 768px, 게임 화면·모달) → `docs/design-review/before/`

**완료 조건:** 새 테스트가 *현재 코드에서는 실패*하고, 실패 항목이 §2.2 진단과 일치한다.

#### Phase 3에서 실제로 걸린 것

1. **`dialog`의 `close` 이벤트를 답으로 삼으면 안 된다.** 확인 다이얼로그를 처음엔
   `close` 이벤트에서 프로미스를 resolve하도록 짰는데, 검증 환경(Chrome 148 미표시 탭)에서
   **`close` 이벤트가 아예 발화하지 않았다.** 새로 만든 빈 `<dialog>`에서도 같았다.
   증상은 조용하다 — 예외도 로그도 없이 `모두 처음으로 되돌리기`와 `새 게임`이 그냥 아무 일도 안 한다.
   → **답은 버튼 클릭 핸들러에서 바로 정하고**, `cancel`/`close`는 Esc·백드롭용 안전망으로만 둔다.
   WebView 구현 편차를 생각하면 실기기에서도 이 편이 안전하다.

2. **미표시 탭에서는 CSS 전환이 진행되지 않는다.** `getComputedStyle`로 잰 값이 전환 전 값에
   머물러 "진행바가 안 움직인다 / 비활성 버튼 색이 안 바뀐다"처럼 보인다. 버그가 아니다.
   `document.visibilityState`를 먼저 확인하고, 최종값을 재려면 `*{transition:none !important}`를
   임시로 주입한 뒤 잰다.

3. **`--ink-disabled`를 한 번 더 낮췄다.** `#756a5e`는 §6.3의 비활성 주요 버튼 면
   (`--surface-mute #f0e9e1`) 위에서 4.38:1로 미달이었다. `#6f6458`로 낮춰 두 면 모두 4.79:1 이상.

#### Phase 4에서 정한 것

1. **문구 마침표는 붙이지 않는다.** §7 표의 예시(`여기는 안 움직여요. 다른 곳을 눌러 보세요`)가
   문장 사이에는 마침표를 쓰고 끝에는 안 쓰는 형태다. 화면 문구 전체를 이 규칙으로 통일했다.
2. **저장소 로드에 타임아웃을 뒀다** (`STORAGE_WAIT_MS` 2.5초). 깜빡임을 없애려고
   `startGame()`을 저장소 로드 뒤로 미뤘는데, 그대로 두면 저장소가 응답하지 않을 때
   스켈레톤에 갇혀 게임을 아예 못 한다. 2.5초를 넘기면 그림 블록으로 먼저 시작하고,
   사진이 늦게 도착하면 그때 다시 그린다.
3. **`.tile.spawned`를 `--m-slow`(400ms)로 올리면서 JS의 대기도 `DROP_MS` 400ms로 맞췄다.**
   기존 330ms 애니메이션에 350ms 대기였다. 애니메이션이 대기보다 길면 낙하 도중에 DOM이 갈린다.
4. **reduced-motion에서는 누름 시 이동을 걷어내고 색으로 바꿨다.** 전역 규칙은 전환 시간만
   줄일 뿐 `:active`의 `translateY`는 그대로 남는다. 이동을 없애되 피드백은 남기라는 §8 요구를
   만족시키려면 `:active` 규칙을 따로 덮어써야 한다.

## 5. DESIGN.md 적용 중 발견한 충돌과 보정 제안

계획 수립 과정에서 DESIGN.md의 토큰 값을 실제로 계산해 검증했다. **§1.2 대비표는 7개 항목 전부 문서값과 일치한다** (오차 0.05 이내). 다만 문서에 없는 조합에서 아래 세 건이 걸린다.

### 5.1 `--line-strong`를 게임판 외곽선으로 쓰면 거의 보이지 않는다

DESIGN §5.3은 게임판 외곽을 `4px solid var(--line-strong)`(#d8c9b8)으로 지정하는데, 실제 대비는

| 조합 | 대비 |
|---|---:|
| `--line-strong` vs 게임판 바닥 `#f6e6d3` | **1.32 : 1** |
| `--line-strong` vs 캔버스 `#fff9f3` | **1.55 : 1** |

게임판 외곽선은 "여기가 노는 영역"을 알리는 구조 경계라 WCAG 1.4.11 기준 3:1이 필요하다.

**제안:** 게임판 전용 토큰 `--board-edge: #96754b`를 신설한다 (바닥 대비 3.48:1, 캔버스 대비 4.07:1).
따뜻한 나무톤을 유지하면서 3:1을 넘긴다. `--line-strong`은 원래 용도인 카드 립·모달 테두리로만 쓴다.

### 5.2 노란 계열 블록이 따뜻한 게임판 바닥에 묻힌다

§1.3 팔레트를 §5.3의 새 바닥색 `#f6e6d3` 위에 올려 계산한 결과다.

| 블록 | 면 vs 바닥 | 립 vs 바닥 |
|---|---:|---:|
| 딸기 `#e2483d` | 3.29 | 5.15 |
| 감귤 `#ff8a1f` | 1.93 | 3.42 |
| **햇살 `#ffc53d`** | **1.29** | **2.41** |
| 새싹 `#34a06a` | 2.69 | 4.95 |
| 하늘 `#3d8fe0` | 2.77 | 4.96 |

바닥색을 어떻게 바꿔도 노란 블록 면이 3:1을 넘기는 조합은 없다(더 어두운 바닥에서는 오히려 1.08까지 떨어진다).
즉 **면 색으로 경계를 만들려는 시도 자체가 성립하지 않는다.** 경계는 립·간격·모양 배지가 담당해야 한다.

**제안:** 햇살 립을 `#c98a00` → **`#9a6800`**(바닥 대비 3.95:1, 자기 면 대비 3.06:1)로 심화한다.
감귤 립은 `#c75e00`(3.42:1)로 유지 가능하다. §1.3 표에 "립은 바닥 대비 3:1 이상" 조건을 추가 명시할 것을 권한다.

### 5.3 좁은 화면에서 블록 68px 하한은 물리적으로 불가능하다

§10은 ≤560px에서 `calc((100vw - 44px - gap*4) / 5)`에 **최소 68px 보장**을 요구한다.
실제 구성 요소(앱 여백×2 + 보드 테두리×2 + 보드 안쪽 여백×2 + 간격×4 + 블록×5)로 계산한 결과다.

|---:|---:|---:|---:|
| 320px | 44.0 | 51.6 | **52.4** |
| 360px | 51.6 | 59.2 | **60.4** |
| 375px | 54.4 | 62.0 | **63.4** |
| 390px | 57.2 | 64.8 | **66.4** |
| 412px | 61.3 | 68.9 | **70.8** |
| 430px | 64.6 | 72.2 | **74.4** |

**68px는 398px 폭부터, 72px는 418px 폭부터** 가능하다. 흔한 360px 기기에서는 어떤 설정으로도 60px가 상한이다.
DESIGN 원안대로 여백을 두면 오히려 현재보다 블록이 **8px 작아진다**는 점도 주의할 것.

→ **[결정 D4](#d4-좁은-화면-블록-크기-가능한-최대치)**: 완화안 수치를 채택하고, DESIGN §10의 "68px 보장"을
"**≥400px에서 68px, 그 이하에서는 확보 가능한 최대**"로 문구를 고친다.

### 5.5 흰 버튼의 테두리·립도 보이지 않는다 (Phase 1에서 발견)

§5.1의 게임판 외곽선과 **같은 종류의 문제**가 버튼에도 있다.
DESIGN §5.1/§5.5는 `.icon-button`·`.wide-button`의 테두리를 `--line`, 립을 `--line-strong`으로 지정한다.

| 조합 | 대비 |
|---|---:|
| `--line` 테두리 vs 캔버스 | **1.26 : 1** |
| `--line-strong` 립 vs 캔버스 | **1.55 : 1** |

흰 버튼(`--surface`)이 크림 캔버스(`--canvas`) 위에 놓이므로 면끼리는 구분되지 않는다.
테두리와 립이 유일한 경계인데 둘 다 보이지 않으면, **어르신은 버튼의 범위를 알 수 없다.**
DESIGN §11 Do의 "버튼에는 항상 **자기 색의 어두운 톤** 립을 준다"는 서술과도 어긋난다 — `#d8c9b8`은 흰 면에 대해 어두운 톤이 아니다.

**제안:** 게임 영역 흰 버튼 전용 토큰 `--btn-edge: #96856f`를 신설한다 (캔버스 대비 3.42:1, 흰 면 대비 3.57:1).
`--line` / `--line-strong`은 모달 내부(조용한 면 위)의 원래 용도로 남긴다 — 그쪽은 §6이 요구하는 톤이 다르다.

> WCAG 1.4.11은 라벨로 식별 가능한 컨트롤의 경계를 면제하므로 규정 위반은 아니다.
> 그러나 저시력 대상 앱에서 "눌리는 면"이 안 보이는 것은 DESIGN §4의 핵심 의도를 무너뜨린다.

### 5.4 비활성 라벨 대비 (참고)

§6.3의 "주요 비활성" 조합(`--ink-faint #9c9084` on `#f0e9e1`)은 **2.59:1**이다.
WCAG는 비활성 컨트롤을 대비 요건에서 면제하므로 규정 위반은 아니지만, 저시력 어르신에게는 라벨이 읽히지 않는다.
**제안:** 비활성 라벨만 `#7a6f63`(4.08:1)로 올린다. "비활성"임은 면 색과 커서로 이미 전달된다.

## 7. 기술 제약 (구현 시 준수)

- `vite.config.js`의 `target: 'chrome60'`은 **JS 문법만** 변환한다. CSS는 그대로 나간다.
- 현재 코드가 이미 `clamp()`, `100dvh`, `aspect-ratio`, `inset`을 쓰므로 실질 하한은 최신 WebView다.
  **새로 도입하지 말 것:** `:has()`, `color-mix()`, CSS 중첩, 컨테이너 쿼리.
  → 립 색은 `color-mix()` 대신 **하드코딩 토큰**으로 정의한다.
- `Path2D.roundRect()` 금지 (`tests/android-compat.test.mjs:6`가 검사 중). `custom-blocks.js`의 기존 `roundedRect()` 헬퍼를 계속 사용한다.
- `index.html` 구조 변경 후 `scripts/verify-build.mjs`가 반드시 통과해야 한다 — 과거 APK 정적 화면 사고의 재발 방지 장치다. ([android-apk-build-incident.md](./android-apk-build-incident.md))

## 9. 결정 사항 (2026-08-03 확정)

| # | 결정 | 근거 |
|---|---|---|
| D1 | 블록 5종의 **이름·아트 유지**, §1.3의 색·립 팔레트만 적용 | 작업량 최소, 프레임 6종의 캐릭터 톤 유지 |
| D2 | 사진 블록을 **슬롯 색 라운드 사각 바탕** 안에 담는다 | CSS 립과 아트 외곽이 정확히 일치, 슬롯 구분 유지 |
| D3 | **Pretendard 동봉하지 않는다** — 현재 폰트 스택 유지 | 오프라인 안정성·APK 용량 우선 |
| D4 | 좁은 화면 블록은 **확보 가능한 최대치** | 68px는 398px 폭부터만 가능 (§5.3) |
| D5 | **핀치 줌 차단 유지** | 줌으로 인한 조작 오차가 더 큰 문제 |
| D6 | `사진 영역` 슬라이더를 **스텝 3에 유지**, 라벨 `사진이 보이는 크기` | 프레임별 적정값이 달라 고정하기 어려움 |

### D1. 슬롯 색 매핑 — 순서가 아니라 색상 계열로 맞춘다

§1.3의 다섯 색을 **슬롯 번호 순서대로** 넣으면 해님이 빨강, 하트가 주황이 되어 이름과 색이 어긋난다.
이름을 유지하기로 한 이상 **색상 계열로 매핑**하는 것이 맞다. 아래 표를 확정안으로 삼는다.

| 슬롯 | 이름(유지) | 면 | 립 | §1.3 원 슬롯 | 배지 |
|---|---|---|---|---|---|
| 0 | 해님 | `#ffc53d` | **`#9a6800`** | 햇살 | ☀ 해 |
| 1 | 하트 | `#e2483d` | `#b32e26` | 딸기 | ♥ 하트 |
| 2 | 별 | `#ff8a1f` | `#c75e00` | 감귤 | ★ 별 |
| 3 | 꽃 | `#34a06a` | `#1f7049` | 새싹 | ✿ 꽃 |
| 4 | 보석 | `#3d8fe0` | `#2464a8` | 하늘 | ◆ 보석 |

해님의 립만 §5.2 보정값 `#9a6800`을 쓴다(원안 `#c98a00`은 보드 바닥 대비 2.41:1로 미달).
이 매핑에서 **다섯 립 모두 보드 바닥 대비 3.42~5.15:1**로 3:1을 넘긴다.

### D1-a. 모양 배지는 유니코드 대신 인라인 SVG로 그린다

다섯 블록 면의 **상호 대비를 계산해 보면 1.03~1.49:1**로, 사실상 밝기가 같다.
즉 **모양 배지는 장식이 아니라 색맹·저시력 사용자에게 유일한 구분 수단**이다.

| 쌍 | 면 대비 |
|---|---:|
| 꽃 vs 보석 | 1.03 |
| 하트 vs 보석 | 1.19 |
| 하트 vs 꽃 | 1.22 |
| 별 vs 꽃 | 1.40 |
| 별 vs 보석 | 1.44 |
| 해님 vs 별 | 1.49 |

그런데 `☀`(U+2600)와 `✿`(U+273F)는 Android에서 **컬러 이모지로 치환되거나 폰트에 없어 두부(□)로 빠질 수 있다.**
구분 수단이 폰트 대체에 좌우되면 안 되므로, 배지는 **인라인 SVG 5종**으로 그린다.
`custom-blocks.js`의 `circle` / `heart` / `polygon` 헬퍼와 같은 형태를 SVG path로 옮기면 된다.

### D2-a. 기존 저장 데이터 마이그레이션이 필요하다

`storage.js`는 **합성이 끝난 dataURL**만 저장한다 (`storage.js:99-104`, 원본 사진은 남지 않는다).
D2로 합성 방식이 바뀌면, 이미 꾸며 둔 블록은 **투명 모서리 그대로 남아 새 CSS 립이 이미지 밖으로 삐져나온다.**

원본 사진이 없어 재합성은 불가능하지만, **저장된 256×256 이미지를 슬롯 색 라운드 사각 위에 다시 얹으면**
새 합성과 동일한 결과가 나온다. 1회성 마이그레이션으로 처리한다.

- 웹: 현재 `WEB_KEY`에 **배열을 그대로** 저장 중 → `{ version: 2, blocks: [...] }`로 감싸고, 배열이면 v1으로 간주해 마이그레이션
- 안드로이드: `loadNativeBlocks()`의 `metadata.version !== 1` 검사를 2로 올리고 v1은 마이그레이션 후 재저장 (`storage.js:60`)

### D5-a. 줌 차단 유지에 따른 보완

확대를 막는 대신 "크게 보고 싶다"는 요구는 아래 두 가지로 받는다.

- **A8 (이번 범위):** 타이포 스케일을 `px` → `rem` 기반으로 정의한다. 브라우저·OS의 글꼴 크기 설정이 그대로 반영되어, 페이지 줌 없이도 글자만 커진다. 버튼 높이와 블록 크기는 `px`를 유지해 레이아웃이 무너지지 않게 한다.
- **B1 (별도 과제, 우선순위 상향):** "더 보기"에 블록 크기 **보통 / 크게** 토글. D5로 사용자가 스스로 키울 수단이 사라졌으므로, 범위 밖 항목 중 가장 먼저 다룰 것을 권한다.
