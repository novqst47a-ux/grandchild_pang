## 1. 목적과 성공 기준

`webapp/`의 현재 UI는 **보라(`--purple #65419a`) + 크림** 톤에 모든 요소가 동일한 립 그림자를 갖고 있어,
게임 화면과 설정 화면의 구분이 시각적으로 없다. DESIGN.md는 이를 다음 대비로 재정의한다.

> **게임 영역은 입체(3D 립) · 모달은 평평(플랫)**, 전체 톤은 따뜻한 크림/주황.

리뉴얼 완료의 판단 기준은 아래 네 가지다.

| # | 성공 기준 | 검증 방법 |
|---|---|---|
| S1 | 게임 영역의 모든 조작 요소가 자기 색의 어두운 립을 갖고 누르면 내려간다 | 실기기 육안 + 코드 리뷰 |
| S2 | 모달 안에 립(`box-shadow: 0 Npx 0`)과 bounce 이징이 하나도 없다 | `tests/design-tokens.test.mjs` 자동 검사 |
| S3 | 사용자에게 보이는 모든 문구가 §7 보이스·톤 규칙을 지킨다 (`-습니다`·금지어 0건) | 자동 문구 검사 |
| S4 | 텍스트 조합 대비 4.5:1 이상, 구조 경계 3:1 이상 | `scripts/check-contrast.mjs` 자동 검사 |

기능(게임 규칙, 저장 방식, 사진 파이프라인)은 **변경하지 않는다.** 이번 작업은 표현 계층과 문구, 그리고 그에 필요한 최소한의 렌더 로직만 다룬다.

### 2.2 반드시 짚어야 할 현재 코드의 문제

1. **`sw.js`의 `ASSETS`에 `styles.css`가 없다** (`webapp/sw.js:2`).
   프리캐시 목록에 없어도 fetch 핸들러가 cache-first로 응답을 저장하므로, 캐시 이름을 올리지 않으면
   **기존 사용자에게 구 CSS가 계속 서빙된다.** 리뉴얼 배포 시 `CACHE` 이름 bump가 필수다.

2. **핀치 줌이 차단되어 있다** (`webapp/index.html:5`의 `maximum-scale=1, user-scalable=no`).
   저시력 사용자 대상 앱에서 확대 차단은 WCAG 1.4.4 위반이며, DESIGN §12 체크리스트의
   "확대 200% 상태 확인" 항목을 애초에 수행할 수 없다. → [질문 Q5](#q5-핀치-줌-차단을-해제할까요)

3. **입체감을 `drop-shadow`로 흉내내고 있다** (`webapp/styles.css:98`).
   DESIGN §5.4가 명시적으로 금지한 방식이다.

4. **전체 초기화가 네이티브 `window.confirm()`을 쓴다** (`webapp/src/app.js:558`).
   DESIGN §9는 별도 확인 다이얼로그 + 기본 포커스 **취소**를 요구한다. 네이티브 confirm은
   문구·색·포커스를 제어할 수 없고, WebView에서 시스템 폰트로 튀어나와 톤이 깨진다.

5. **선택지가 가로 스크롤로만 접근된다** (`webapp/styles.css:172`의 `.slot-list, .frame-list`).
   DESIGN §11 Don't에 정면으로 어긋난다.

## 3. 작업 단계

각 단계는 독립 커밋/PR로 나눈다. 단계마다 `npm.cmd test && npm.cmd run check`가 통과해야 다음으로 넘어간다.

### Phase 0 — 안전망 (0.5일)

리뉴얼 자체보다 **먼저** 넣는다. 이후 단계의 회귀를 자동으로 잡기 위한 장치다.

- [ ] `webapp/scripts/check-contrast.mjs` 신규 — `styles.css`의 `:root`에서 토큰을 파싱해 선언된 조합의 WCAG 대비를 계산하고, 텍스트 4.5:1 / 구조 경계 3:1 미만이면 종료 코드 1
- [ ] `webapp/tests/design-tokens.test.mjs` 신규 — 아래를 자동 검사
  - `--purple` / `--cream` 등 구 토큰 잔존 0건
  - `color: var(--carrot)` 형태의 **밝은 주황 위 텍스트** 사용 0건
  - `font-weight` 값이 `400 / 700 / 800 / 900` 집합 밖이면 실패
  - 모달 선택자(`.settings-dialog` 이하) 안에 `box-shadow: 0 Npx 0` 립 0건
  - `index.html` 텍스트 노드 + `app.js` 문자열 리터럴에 `-습니다` 및 금지어(`오류`, `실패`, `잘못`, `불가능`, `데이터가 없습니다`) 0건
- [ ] `package.json`의 `check` 스크립트에 위 두 개 연결
- [ ] 리뉴얼 전 기준 스크린샷 확보 (360 / 390 / 768px, 게임 화면·모달) → `docs/design-review/before/`

**완료 조건:** 새 테스트가 *현재 코드에서는 실패*하고, 실패 항목이 §2.2 진단과 일치한다.

### Phase 1 — 토큰과 타이포 기반 (0.5일)

레이아웃은 그대로 두고 색·글자만 바꾼다. 되돌리기 가장 쉬운 단계.

- [ ] `styles.css`의 `:root`를 DESIGN §1.1 / §3 / §8 값으로 교체 (구 토큰 완전 제거)
- [ ] 본문 19px, 좁은 화면 18px, 굵기 400/700/900 정리 (`font-weight: 950` 3곳 → 900)
- [ ] `font-variant-numeric: tabular-nums`를 점수·이동 숫자에 적용 (현재 `.score-card strong`에만 있음 → 유지·확인)
- [ ] `meta[name=theme-color]` → `#fff9f3`, `manifest.webmanifest`의 `background_color`/`theme_color` 동일 적용
- [ ] 포커스 링 `#1078d0` → `var(--focus)` (`styles.css:39`)

**완료 조건:** `check-contrast.mjs` 통과. 화면은 주황 톤이지만 아직 평면적이어도 됨.

### Phase 2 — 게임 영역 입체화 (1.5일)

- [ ] `.tile`: `drop-shadow` 제거 → `box-shadow: 0 6px 0 var(--lip)`, `:active { transform: translateY(6px); box-shadow: none; }`
      `--lip`은 `renderBoard()`가 슬롯별로 인라인 지정 (`webapp/src/app.js:107` 부근)
- [ ] `.tile` 안에 **모양 배지** DOM 추가 — 우상단 22px 반투명 흰 원 + 슬롯 글리프, `aria-hidden="true"`
- [ ] `custom-blocks.js`의 기본 블록 아트를 `roundedRect(5,5,246,246,47)` → **256 전면**으로 변경.
      CSS `border-radius` + `overflow:hidden`이 클리핑을 맡아야 CSS 립과 아트 외곽이 정확히 맞는다.
- [ ] 사진 블록도 슬롯 색 라운드 사각 위에 프레임을 얹는 구조로 변경 → [질문 Q2](#q2-사진-블록의-프레임을-슬롯-색-바탕-안에-담을까요)
- [ ] `.board`: 배경 `#f6e6d3`, `--tile-gap`을 `clamp(3px,1vw,8px)` → `clamp(6px,1.8vw,10px)`
- [ ] 점수판 색 재배치: 점수=`--carrot-deep`, 남은 이동=`--reward`+`--ink`, 안내=`--surface`+`0 4px 0 --line-strong`
- [ ] **남은 이동 3 이하 경고 상태** 신규 — `--danger` 면 + 흰 글자 + 1회 펄스 + 라벨을 `이제 3번 움직일 수 있어요`로
- [ ] `.wide-button` / `.primary-button` 높이 58px → **64px**, `.icon-button` 56px 하한 확인
- [ ] `.drag-ghost` 링 색 `#65419ac9` → `var(--focus)` 5px (`styles.css:115`)
- [ ] 종료 오버레이 `--yellow` → `--reward`, 키커·점수 색 `--carrot-deep`

**완료 조건:** 실기기에서 블록·버튼을 누를 때 명확히 "내려가는" 피드백이 보인다.

### Phase 3 — 꾸미기 모달 스텝화 (2일, 가장 큰 단계)

현재 `<form method="dialog">`가 헤더/푸터를 감싸고 있어 **내부 버튼이 전부 모달을 닫는다.**
스텝 이동 버튼을 넣으려면 이 구조를 먼저 걷어내야 한다.

- [ ] `index.html`의 모달을 아래 구조로 재작성

```
헤더  : [← 뒤로(56px, step>1)]  제목 Title 30/900  [×(56px)]
진행바: 4px, 트랙 --line / 채움 --carrot, 폭 250ms 애니메이션
본문  : .step-panel[data-step="1|2|3|done"] 중 하나만 표시
푸터  : sticky, 주요 버튼 1개만 (폭 100%, 높이 64px, 립 없음)
```

- [ ] `app.js`에 스텝 상태기계 추가
      `{ step: 1|2|3|'done', slot, photo, frame, holeScale, transform }`
      푸터 버튼 라벨/활성 상태를 스텝별로 전환
      - 1: `다음` (항상 활성)
      - 2: `다음` (사진 없으면 비활성 + 보조문구 `사진을 먼저 골라 주세요`)
      - 3: `이 사진으로 할게요`
      - done: `게임으로 돌아가기` + 본문에 `계속 꾸미기` 보조 버튼
- [ ] `.slot-list` / `.frame-list` 가로 스크롤 → **3열 그리드**, 카드 최소 96×96, 간격 12px
      선택 시 `--focus-tint` 면 + `3px --focus` 테두리 + 우상단 체크 원 + "선택됨" 텍스트 유지
- [ ] 프리셋 3종 + 칭찬 효과 자리를 **스텝 1 하단 "더 보기"** 안으로 이동 (`<details>` 사용)
- [ ] `#cropHint` 오버레이 → 캔버스 **아래 상시 표시** Body-S 안내로 이동
- [ ] 슬라이더에 좌우 `−`/`+` 56px 버튼 추가, 손잡이 36px, 트랙 12px, 터치 영역 48px, `accent-color: var(--carrot-deep)`
- [ ] 모달 안 모든 `box-shadow` 립 제거, `--e-bounce` 사용 금지 확인
- [ ] 스텝 전환 = 페이드 + 8px 상승 (250ms `--e-enter`), 좌우 슬라이드 금지
- [ ] ≤560px에서 모달을 전체 화면 시트로 (상단만 radius 28px)
- [ ] `window.confirm()` 제거 → 기존 `#confirmDialog`를 재사용 가능한 확인 다이얼로그로 일반화, **기본 포커스는 취소**

**완료 조건:** `npm.cmd test && npm.cmd run check` 통과.

### Phase 4 — 문구·상태·모션 (1일)

- [ ] §7 보이스·톤 표대로 문구 일괄 교체 (아래 §4 대응표)
- [ ] 토스트: `--success` / `--danger` 변형 추가, radius `--r-full`, 표시 1800ms → **2500ms**
- [ ] 첫 진입 스켈레톤 25칸 — 현재 `startGame()`이 저장소 로드보다 먼저 렌더해서 기본 블록 → 사진 블록으로 한 번 깜빡인다 (`app.js:572` 부근). 스켈레톤으로 이 깜빡임을 함께 없앤다
- [ ] 연쇄 처리 중 상태를 `disabled`(현재 `cursor:wait`) → `pointer-events:none` + 밝기 96% 병행
- [ ] 모션 토큰 `--m-*` / `--e-*` 도입, `--e-bounce`는 게임 영역 선택자에서만 참조
- [ ] `prefers-reduced-motion`에서 **누름 시 색 변화는 유지** (현재는 전역 `transition-duration: .01ms`로 일괄 축소만 — `:active` 색 변화 규칙을 별도로 남길 것)
- [ ] 잘못된 이동에 짧은 진동 추가 (`navigator.vibrate?.(20)`) — 소리를 끈 어르신에게도 피드백이 남도록

### Phase 5 — 검증과 배포 (0.5일)

- [ ] GitHub Pages에 배포한 PWA를 실기기에서 설치하고 오프라인 실행 확인
- [ ] 수동 점검: 360 / 390 / 768px, 브라우저 확대 200%, TalkBack, `prefers-reduced-motion`, 한 손 조작
- [ ] 리뉴얼 후 스크린샷 → `docs/design-review/after/`

| `app.js:579-583` | …유지**됩니다** / 저장소를 열지 못했**습니다**. …이용해주세요. | 사진은 이 기기에만 저장돼요 / 자동 저장이 안 돼요. 꾸민 모습 저장하기를 써 보세요 |
| `app.js:558` | window.confirm(…삭제**됩니다**.) | 확인 다이얼로그로 대체 (기본 포커스 취소) |

용어 치환: **프리셋 → 꾸민 모습**, **슬롯 → 블록 자리**, **크롭/자르기 → 사진 맞추기**, **초기화 → 처음으로 되돌리기**.

## 5. DESIGN.md 적용 중 발견한 충돌과 보정 제안

계획 수립 과정에서 DESIGN.md의 토큰 값을 실제로 계산해 검증했다. **§1.2 대비표는 7개 항목 전부 문서값과 일치한다** (오차 0.05 이내). 다만 문서에 없는 조합에서 아래 세 건이 걸린다.

### 5.1 `--line-strong`를 게임판 외곽선으로 쓰면 거의 보이지 않는다

DESIGN §5.3은 게임판 외곽을 `4px solid var(--line-strong)`(#d8c9b8)으로 지정하는데, 실제 대비는

| 조합 | 대비 |
|---|---:|
| `--line-strong` vs 게임판 바닥 `#f6e6d3` | **1.32 : 1** |
| `--line-strong` vs 캔버스 `#fff9f3` | **1.55 : 1** |

게임판 외곽선은 "여기가 노는 영역"을 알리는 구조 경계라 WCAG 1.4.11 기준 3:1이 필요하다.

**제안:** 게임판 전용 토큰 `--board-edge: #96754b`를 신설한다 (바닥 대비 3.48:1, 캔버스 대비 4.07:1).
따뜻한 나무톤을 유지하면서 3:1을 넘긴다. `--line-strong`은 원래 용도인 카드 립·모달 테두리로만 쓴다.

### 5.2 노란 계열 블록이 따뜻한 게임판 바닥에 묻힌다

§1.3 팔레트를 §5.3의 새 바닥색 `#f6e6d3` 위에 올려 계산한 결과다.

| 블록 | 면 vs 바닥 | 립 vs 바닥 |
|---|---:|---:|
| 딸기 `#e2483d` | 3.29 | 5.15 |
| 감귤 `#ff8a1f` | 1.93 | 3.42 |
| **햇살 `#ffc53d`** | **1.29** | **2.41** |
| 새싹 `#34a06a` | 2.69 | 4.95 |
| 하늘 `#3d8fe0` | 2.77 | 4.96 |

바닥색을 어떻게 바꿔도 노란 블록 면이 3:1을 넘기는 조합은 없다(더 어두운 바닥에서는 오히려 1.08까지 떨어진다).
즉 **면 색으로 경계를 만들려는 시도 자체가 성립하지 않는다.** 경계는 립·간격·모양 배지가 담당해야 한다.

**제안:** 햇살 립을 `#c98a00` → **`#9a6800`**(바닥 대비 3.95:1, 자기 면 대비 3.06:1)로 심화한다.
감귤 립은 `#c75e00`(3.42:1)로 유지 가능하다. §1.3 표에 "립은 바닥 대비 3:1 이상" 조건을 추가 명시할 것을 권한다.

### 5.3 좁은 화면에서 블록 68px 하한은 물리적으로 불가능하다

§10은 ≤560px에서 `calc((100vw - 44px - gap*4) / 5)`에 **최소 68px 보장**을 요구한다.
360px 폭 기기에서 계산하면:

```
gap = clamp(6px, 1.8vw=6.5px, 10px) = 6.5px
(360 - 44 - 26) / 5 = 58px
```

68px를 만들려면 최소 `5×68 + 4×6 + 44 = 408px` 폭이 필요하다. 여백과 간격을 최대한 줄여도 360px 기기에서는 약 62px가 상한이다.
→ [질문 Q4](#q4-좁은-화면-블록-최소-68px-를-어떻게-처리할까요)

### 5.4 비활성 라벨 대비 (참고)

§6.3의 "주요 비활성" 조합(`--ink-faint #9c9084` on `#f0e9e1`)은 **2.59:1**이다.
WCAG는 비활성 컨트롤을 대비 요건에서 면제하므로 규정 위반은 아니지만, 저시력 어르신에게는 라벨이 읽히지 않는다.
**제안:** 비활성 라벨만 `#7a6f63`(4.08:1)로 올린다. "비활성"임은 면 색과 커서로 이미 전달된다.

## 7. 기술 제약 (구현 시 준수)

- 번들러와 트랜스파일 단계를 사용하지 않으므로 브라우저가 원본 JS와 CSS를 직접 해석한다.
- 현재 코드가 이미 `clamp()`, `100dvh`, `aspect-ratio`, `inset`을 쓰므로 실질 하한은 최신 모바일 브라우저다.
  **새로 도입하지 말 것:** `:has()`, `color-mix()`, CSS 중첩, 컨테이너 쿼리.
  → 립 색은 `color-mix()` 대신 **하드코딩 토큰**으로 정의한다.
- `Path2D.roundRect()` 대신 `custom-blocks.js`의 기존 `roundedRect()` 헬퍼를 계속 사용한다.
- `index.html`과 서비스 워커의 오프라인 자산 목록을 함께 관리한다.

## 9. 결정이 필요한 질문

각 질문에 **답변 예시**를 함께 적었다. 그대로 골라 주셔도 되고, 다른 안을 주셔도 된다.

### Q1. 블록 5종의 이름과 아트를 어떻게 할까요?

DESIGN §1.3은 **딸기·감귤·햇살·새싹·하늘 (●◆★▲■)**을 제시하는데,
현재 `custom-blocks.js:66-72`는 **해님·하트·별·꽃·보석**으로 캔버스 아트까지 그려져 있습니다.

- **답변 예시 A (권장):** "이름과 아트는 지금 것을 유지하고, §1.3의 색·립 팔레트만 순서대로 매핑해 주세요. 모양 배지는 현재 아트에 맞춰 ☀ ♥ ★ ✿ ◆로 하고요."
  → 작업량 최소, 프레임 6종(토끼·곰·고양이…)의 캐릭터 톤과도 어긋나지 않음
- **답변 예시 B:** "DESIGN대로 전면 교체해 주세요. 과일·자연물 쪽이 어르신에게 더 친숙합니다."
  → 기본 블록 아트 5종 재작업 필요, +1일
- **답변 예시 C:** "이름만 §1.3으로 바꾸고 아트는 유지해 주세요."
  → 이름과 그림이 어긋나 오히려 혼란. 비권장

### Q2. 사진 블록의 프레임을 슬롯 색 바탕 안에 담을까요?

DESIGN §1.3은 사진 블록도 "립·테두리·모양 배지는 슬롯 색을 유지"하라고 합니다.
그런데 현재 프레임(토끼 귀, 하트 실루엣 등)은 **투명 배경 위 불규칙 형태**라, CSS 라운드 사각 립이 실루엣 밖으로 삐져나옵니다.

- **답변 예시 A (권장):** "슬롯 색 라운드 사각 바탕을 깔고 그 안에 프레임+사진을 넣어 주세요. 손자 사진 5장이 비슷해도 자리별로 구분되는 게 더 중요합니다."
- **답변 예시 B:** "프레임 실루엣을 살리고 싶으니 립은 캔버스에 함께 그려 주세요."
  → 립이 이미지의 일부가 되어 `:active` 시 함께 움직이므로 "눌리는 느낌"이 사라짐
- **답변 예시 C:** "사진 블록만 립 없이 가도 됩니다."
  → 게임판에 입체/평면이 섞임. DESIGN 핵심 원칙과 충돌

### Q3. Pretendard 폰트를 도입할까요?

DESIGN §2.1은 `Pretendard Variable`을 1순위로 지정하지만, 이 앱은 **오프라인 PWA**라 CDN을 쓰지 않고 시스템 폰트를 우선합니다.

- **답변 예시 A (권장):** "동봉하지 말고 현재대로 Noto Sans KR → 시스템 폰트 순서를 유지해 주세요. 오프라인 안정성과 초기 다운로드 크기가 더 중요합니다."
  → DESIGN §2.1의 폰트 스택에서 Pretendard만 제거. 굵기 400/700/900 규칙은 그대로 지킴
- **답변 예시 B:** "Regular/Bold/Black 3종을 한글 서브셋으로 동봉해 주세요."
  → 초기 다운로드 +600KB~1.5MB, 서브셋 생성 스크립트 추가 필요

### Q4. 좁은 화면 블록 최소 68px를 어떻게 처리할까요?

§5.3에서 계산했듯 360px 폭 기기에서는 최대 약 62px입니다.

- **답변 예시 A (권장):** "여백과 간격을 줄여 확보 가능한 최대치(약 62px)를 쓰고, DESIGN §10의 '68px 보장'을 '가능한 최대'로 완화해 주세요."
- **답변 예시 B:** "68px를 고정하고 게임판만 가로 스크롤을 허용해 주세요."
  → §11 Don't(가로 스크롤 선택지)와 충돌하고, 5×5가 한눈에 안 들어옴
- **답변 예시 C:** "68px를 유지하되 아주 좁은 화면에서는 격자를 줄여 주세요."
  → 게임 규칙 변경. 비권장

### Q5. 핀치 줌 차단을 해제할까요?

현재 `index.html:5`가 `maximum-scale=1, user-scalable=no`로 확대를 막고 있습니다.

- **답변 예시 A (권장):** "해제해 주세요. 저시력 사용자가 확대할 수 있어야 합니다."
- **답변 예시 B:** "유지해 주세요. 게임 중 실수로 확대되는 게 더 혼란스럽습니다."
  → 이 경우 DESIGN §12의 "확대 200% 확인" 항목은 수행 불가로 처리하고 체크리스트에서 제외

### Q6. `사진 영역`(holeRange) 슬라이더를 어디에 둘까요?

DESIGN §6.5는 스텝 3에 **사진 크기 슬라이더 하나**만 언급합니다. 현재는 `사진 영역` 슬라이더가 하나 더 있습니다 (`index.html:110-111`).

- **답변 예시 A (권장):** "스텝 3에 남기되 라벨을 `사진이 보이는 크기`로 바꿔 주세요."
- **답변 예시 B:** "'더 보기'로 옮겨 스텝을 더 단순하게 해 주세요."
- **답변 예시 C:** "제거하고 82%로 고정해 주세요."
  → 프레임별로 적정값이 달라 일부 프레임에서 사진이 답답해 보일 수 있음
