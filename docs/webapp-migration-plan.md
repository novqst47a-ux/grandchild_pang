# 매치3 퍼즐 웹앱 전환 검토

작성일: 2026-08-03

## 1. 배경

현재 `practice/sonjupang/`에 Godot 4.7로 매치3 퍼즐을 연습 구현 중.
여기에 **사용자 사진을 블록 이미지로 쓰는 기능**을 추가하면서, 모바일(안드로이드) + 웹앱으로
서비스하는 방향을 검토했다.

### 추가하려는 기능

- 사용자가 사진을 업로드하거나 직접 촬영해서 블록 이미지 및 파티클로 사용
- 예시 흐름: 가운데가 뚫린 '토끼 얼굴 프레임' 선택 → 인물 사진 추가 → 얼굴 부분을 크롭
  → `토끼 프레임 + 인물 얼굴` 블록 완성
- 사진 데이터는 **서버 업로드 없이** 폰/브라우저에 저장
- 사용자가 직접 초기화하기 전까지 유지

### 서비스 제약

| 항목 | 내용 |
|---|---|
| 공개 범위 | 지인·가족 수준의 제한적 공개 |
| 회원/광고 | 없음 |
| 앱 출시 | 정식 스토어 출시 불가 |
| 서버 | 지양. 꼭 필요하면 Supabase만 사용 가능 |
| 배포 형태 | 웹페이지 또는 단일 앱 |
| 유지보수 | 보안 기능 추가·유지보수 어려움. 단발성 가능성 높음 |

## 2. 결론

**Godot 웹 익스포트가 아니라, 웹 네이티브(Phaser 3 / PixiJS + PWA)로 다시 만드는 것을 권장.**

성능 문제가 아니라 **사진 기능** 때문이다.

### Godot 웹 익스포트를 택하지 않는 이유

Godot 4의 웹 익스포트 자체는 2D라면 모바일 브라우저에서도 동작한다.
다만 웹에서는 Compatibility 렌더러만 지원되고(Forward+/Mobile 렌더러 미지원),
초기 로딩 용량이 크다는 알려진 제약이 있다.

진짜 문제는 이것이다.

- 카메라/갤러리 열기, 크롭 UI(핀치 줌), IndexedDB 저장은 **전부 브라우저 API**다
- Godot에서 쓰려면 `JavaScriptBridge`로 JS 코드를 문자열로 넘기고
  `Blob → base64 → 이미지 디코딩`을 수동으로 왕복시켜야 한다
- 가능은 하지만, **앱의 핵심 기능이 가장 취약한 부분이 된다**

### 포팅 부담은 크지 않다

매치 판정, 낙하, 연쇄 처리 같은 게임 로직은 언어에 의존하지 않는다.
현재 `board.gd`(약 300줄)에 있는 로직은 그대로 옮겨갈 수 있다.

현재 구현되어 있는 것:

- 8×8 그리드, 5종 타일 (`board.gd`)
- 타일 스왑/매치/낙하/콤보 (`piece.gd`, `combo_popup.gd`)
- 점수 UI, 게임오버 다이얼로그, 시작 메뉴
- 파티클 이펙트 (`pop_particle.gd`), BGM/효과음

## 3. 추천 스택

```
Phaser 3 (또는 PixiJS) + TypeScript + Vite
  → PWA (manifest + service worker)
  → Cloudflare Pages / GitHub Pages 정적 배포
```

**서버 불필요.** Supabase도 현재 요구사항에는 쓰지 않는다.
랭킹 기능을 나중에 넣고 싶어질 때만 다시 고려한다.

프레임워크 선택 기준:

- **Phaser 3** — 씬 관리, 트윈, 입력 처리가 내장. Godot에서 넘어오기에 개념이 가장 가깝다
- **PixiJS** — 렌더러만 제공. 더 가볍지만 게임 루프를 직접 짜야 한다

매치3처럼 씬/트윈 의존도가 높은 장르라면 Phaser 3이 무난하다.

## 4. 사진 블록 기능 구현 설계

### 4.1 입력

```html
<input type="file" accept="image/*" capture="environment">
```

안드로이드 크롬에서 카메라/갤러리 선택 시트가 뜬다. **별도 권한 처리 코드 불필요.**

### 4.2 디코딩 (EXIF 회전 보정)

```js
const bitmap = await createImageBitmap(file, { imageOrientation: 'from-image' });
```

`imageOrientation: 'from-image'`를 빼먹으면 **세로로 찍은 사진이 눕는다.** 반드시 지정할 것.

### 4.3 크롭 UI

- 프레임의 구멍 모양을 오버레이로 보여주고, 그 안에서 사진을 팬/줌 시키는 방식
- **Pointer Events** 사용 (한 손가락 드래그 + 두 손가락 핀치 줌)
- 직접 구현하거나 `cropperjs` 사용

### 4.4 합성 (프레임 + 얼굴)

오프스크린 canvas에서 `globalCompositeOperation`으로 마스킹한다.

```
1. 마스크 PNG 그리기            (구멍 부분 = 불투명)
2. globalCompositeOperation = 'source-in'
   → 사진 그리기                (구멍 안쪽에만 남음)
3. 프레임 PNG를 위에 합성
```

결과물은 **256×256 WebP blob**으로 저장하고, 원본 사진은 버린다.

### 4.5 저장

- **IndexedDB** 사용 (`idb` 라이브러리 권장)
  - `localStorage`는 5MB 한계라 이미지 저장에 부적합
- `navigator.storage.persist()`를 호출해 브라우저 자동 정리를 방지
- 안드로이드 크롬은 안정적
- iOS Safari는 7일 미사용 시 삭제될 수 있으나, **홈 화면에 추가(PWA 설치)** 하면 거의 해결됨
- "데이터 초기화" 버튼 = IndexedDB clear 한 줄

### 4.6 블록 제거 연출 / 파티클

> **사진을 조각내거나 부수는 연출은 사용하지 않는다.**
> 고령자가 손주나 가족 사진을 넣어 쓰는 경우가 많고, 그 얼굴이 산산조각 나는 연출은
> 심리적으로 불쾌하게 받아들여진다. 기술적으로 구현이 쉽다는 이유로 채택해서는 안 된다.

대신 다음 방향으로 처리한다.

- 블록이 살짝 커졌다가 **부드럽게 축소되며 페이드아웃** — 사진은 마지막까지 온전한 형태 유지
- 사라진 자리에 **프레임 색상 기반의 반짝임/별 파티클**이 퍼짐
- 위로 살짝 떠오르며 사라지는 연출도 잘 어울린다

즉 "부서진다"가 아니라 **"칭찬받고 사라진다"** 는 인상이 목표다.

파티클은 사진과 무관한 별도 스프라이트(반짝임, 작은 별)를 코드로 생성해 재사용한다.

## 5. 게임 디자인상 주의점 (중요)

**사진 블록은 서로 구분이 어렵다.**

얼굴 사진 6종을 나란히 놓으면 매치3의 핵심인 "한눈에 색 구분"이 무너진다.

대응 방향:

- 프레임 자체를 **강한 단색 + 뚜렷한 실루엣**(토끼 / 곰 / 개구리)으로 제작
- 사진은 **가운데 작은 영역만** 차지하게 한다
- 즉 **프레임이 게임 피스이고, 사진은 장식**이라는 비율이 안전하다

이 부분이 검증에 실패하면 게임 디자인 자체를 조정해야 하므로,
프로토타입에서 가장 먼저 확인해야 한다.

## 6. 배포

- 정적 호스팅에 올리고 **URL만 지인에게 전달**하면 끝
- 안드로이드에서 "홈 화면에 추가" → 전체화면 실행, 오프라인 동작
- 나중에 진짜 APK가 필요하면 **Capacitor**로 감싸서 파일로 직접 전달 가능 (스토어 불필요)
- 데이터가 전부 로컬에 있고 서버가 없으므로 **보안 유지보수 부담이 사실상 없다**
